## Review feature parity and evidence

**Feature parity** describes whether GUI-QML achieves the user outcomes supported by Qt Widgets. **Evidence** shows what supports that assessment: application captures, source connections and scoped test assertions. **Acceptance** records the review decision based on the implementation and its proof.

The 182 subfeatures are counted once across 34 groups. The **Parity gaps** count includes partially implemented and missing outcomes. Parity, evidence coverage and review decisions remain separate so reviewers can distinguish implementation work from proof or follow-up work.

For example, **Create and Export PSBT** covers transferring an unsigned transaction to another signing application while preserving recipients and amounts. Captures show the workflow, and targeted assertions support the preservation of the transaction. A reviewer uses that evidence to accept the outcome or identify remaining work.

Items with parity and **Full GUI-QML evidence** default to **Accepted** under the recorded review standard: targeted automation with a matching capture, reviewed QML with connected integration hooks and relevant existing tests, or a screenshot explicitly accepted for that subfeature. An unresolved recorded failure prevents that default. Reviewers can accept or reopen an item and set it as needed for merge, needed for release or not needed. Saved choices take precedence over defaults and can be exported for project review. These local decisions do not change the underlying parity or evidence assessments.

- Dark mode is the default. Use the sun/moon button in the top bar to switch themes; the browser remembers your preference. Original application captures keep their recorded colors.
- Search feature names, subfeature IDs, and evidence descriptions. Press `/` to focus search.
- Filter GUI-QML by **Parity**, **Partial parity**, or **Not implemented**. In Groups view this applies to the entire feature group; in Subfeatures view it applies to individual capabilities. Qt Widgets stays visible as the reference in comparisons and galleries.
- Combine implementation parity with requirements, evidence coverage, capture availability, feature area, and personal review status. Full evidence means targeted automation with a matching capture, an explicitly reviewed QML workflow with tests/hooks, or a screenshot explicitly accepted for that subfeature. An unresolved recorded failure prevents Full coverage. Partial evidence includes the remaining subfeatures. Evidence coverage and implementation parity are separate assessments. Cards using the integration review are labeled **QML + tests/hooks** and link the reviewed modules and existing passing tests. Their original runtime records remain expandable; no new application test run is claimed.
- Switch between feature groups and individual subfeatures. The summary shows **Total subfeatures**, **Parity gaps**, and **Accepted**. Select either linked count to open its subfeature filter. Use the evidence and parity filters together to find implemented items with incomplete proof. **Not accepted** includes everything without an Accepted decision, including outstanding implementation, proof, and review work. Filter state is included in catalog links.
- Open a group for per-subfeature application comparisons, modules/tests, or a capture gallery.
- Inspect original screenshots with full-size zoom, timestamps, hashes, and keyboard navigation.
- Use the checkmark at the bottom of a subfeature card to toggle **Accepted**. **Review details** opens the full dialog for acceptance status, notes and follow-up work. Select **Use evidence default** to restore automatic acceptance. Defaults are labeled **Accepted · evidence default**. Quick changes preserve notes and scope.
- Mark a feature **Needed for merge**, **Needed for release**, or **Not needed**. Full-parity groups and subfeatures default to **Needed for merge**; partial and missing items stay **Unassigned**. Requirement defaults use implementation parity. Acceptance defaults additionally require Full GUI-QML evidence.
- Set a group choice using **Merge / release scope → Change** on its feature page; click a subfeature's scope label (such as **Needed for merge**) to choose another scope or restore **Use default**. Changes save immediately. A saved group choice takes precedence over automatic subfeature defaults; individual overrides take precedence over both. Existing choices, including explicit Unassigned, are preserved. An automatic full-parity group rating alone does not assign missing secondary subfeatures to merge.
- Filter **Acceptance scope** in Groups view to match group choices, or in Subfeatures view to match individual choices including inherited defaults. Requirement choices are independent of acceptance status. Changing a requirement preserves the acceptance choice or evidence default.

Reviews are stored only in the browser, keyed to the exact evidence snapshot. They are not submitted to the hosting service or written into the evidence pack. Import preserves existing differing records and reports conflicts. A different snapshot is rejected. If browser storage is unavailable, export before closing the page. Moving between the local file and a hosted origin requires export/import.

Review exports use schema version 4 and include the catalog revision, current `reviews`, original `priorReviews`, removed-subfeature `retiredReviews`, and the automatically accepted IDs. Versions 1–3 remain importable. Existing statuses override automatic acceptance; use Review details to restore the evidence default when wanted. Default statuses remain `default`, so scope edits and notes do not turn automatic acceptance into a manual decision. The storage key includes the catalog revision to isolate decisions from older open tabs. The previous v4 catalog migrates automatically: F28.S03’s saved record moves to `retiredReviews`, while other decisions and original notes are preserved. Its acceptance and scope do not transfer to another subfeature. Review imports accept this explicitly compatible prior revision; unrelated catalog revisions and different evidence snapshots are rejected. Old notes remain separate from current decisions; reviewing a consolidated subfeature never overwrites its original records.

The Accepted count includes both automatic evidence defaults and explicit saved acceptances. Reviewed remains available for older or ongoing reviews without accepting an item. Evidence levels, the resolved test failure and its history, and original scope limitations remain visible. Automatic acceptance requires both parity and Full GUI-QML evidence, including explicitly recorded screenshot acceptance. A screenshot without that decision or a related passing suite alone is not sufficient.

Implementation parity is a rough assessment of whether the main user goal is achieved at the pinned source revisions. Equivalent workflows count as fully implemented: for example, exporting a file instead of copying to the clipboard, or restoring the main window to reach an action instead of using a tray shortcut. Important missing capabilities, incompatibilities, and broken outcomes remain partial or not implemented. Missing captures or untested hardware do not imply missing implementation. Information counts as implemented only when the user can identify the value and its meaning. Pending payments are verified by a visible amount and a passing confirmation scenario. F07.S01 remains partial because a separate regression leaves the wallet balance stale after a mining reward matures. This is an observed failure, not a missing label or screenshot.

Each group has an explicit main goal, status, and rationale in [`data/implementation.json`](data/implementation.json), shown on its feature page. Its rating is judged independently of the subfeature tally. Wallet creation can reach parity while standalone blank-wallet creation remains a secondary gap; in-app error dialogs do not fulfill the desktop-notification goal. Each subfeature also has a reasoned assessment. Original detailed comparisons and evidence remain archived, with dated addenda applied to the current view, so reviewers can inspect exact differences and make their own acceptance decisions.

## Source and regeneration

`src/` contains the application HTML, CSS, JavaScript, and icon. The runtime has no external dependencies. `scripts/build.py` reads the original Markdown and JSON evidence, generates `dist/data.js`, applies the dated addenda in `data/reruns/` and evidence collections in `data/collections/`, and copies the unmodified original records and rerun artifacts into `dist/gui-feature-evidence/`. The original catalog identity is preserved while current results, captures, and explicitly reassessed subfeatures are updated. `data/catalog-audit.json` records the reviewed IDs, findings and approved merges; `scripts/catalog.py` applies them after the evidence addenda and produces the current catalog and audit. Original snapshot files remain unchanged. Retired subfeature IDs have one or several current destinations, while totals count only active subfeatures. Scope-specific assessment overrides live in the audit; original per-subfeature assessments stay archived. Combined proof keeps the least complete evidence level unless a narrowed scope has an explicit, justified reassessment. A rerun can supersede a gallery capture while its original bytes and historical links remain available in the archive. Existing saved reviews and explicit requirements are preserved; parity-based automatic defaults follow the updated assessment.

```bash
python3 -m pip install -r requirements-build.txt
python3 scripts/build.py
python3 scripts/validate.py
node --check src/app.js
```

The builder regenerates from the bundled snapshot under `dist/gui-feature-evidence/`. To intentionally replace that snapshot, pass `--evidence /path/to/gui-feature-evidence`. Screenshot bytes and evidence statuses are checked against the original manifests and dated collection records. All feature modules and source links remain pinned to the reviewed revisions.

Commit both the source edits and regenerated `dist/` output. CI rebuilds the site and fails if the committed output is stale. The bundled snapshot makes a fresh clone self-contained.

Update `data/implementation.json` when implementation changes are reviewed. Schema version 2 requires a status and reason for every group and subfeature, plus a main user goal for every group. The builder rejects missing or extra assessments and references to a different evidence snapshot or source revision. Generated `dist/current-assessments.json` exposes current assessments after the audit; `dist/implementation.json` retains the original 203-subfeature assessment. Keep scope rewrites in `data/catalog-audit.json` consistent when recording new evidence. These assessments preserve the existing evidence snapshot identity and saved review compatibility.

## Validation

`scripts/browser-test.cjs` exercises the browser interactions using the workspace's existing Puppeteer image. It expects `/site` to contain this project and `/qa` to be a writable, disposable results directory. Run as root with `PUPPETEER_CACHE_DIR=/home/pptruser/.cache/puppeteer`; Chrome runs in the container with `--no-sandbox`. The container may use `--network none`: the test server uses loopback only.

The checks cover old-ID redirects and replacement pages, review migration across merged/split scopes and groups, preserved history, import validation, filters, direct links, all 34 feature routes, all 218 selected images, local-file access, screenshot zoom, note persistence/escaping, review import/export, current results and historical failure reporting, and mobile navigation/layout. The Pages workflow runs these checks under `/bitcoin-gui-evidence/` to verify project-relative asset links.

Run the same browser checks locally with Docker:

```bash
mkdir -p .validation/browser
docker run --rm --init --network none --user 0 --shm-size=256m \
  -e PUPPETEER_CACHE_DIR=/home/pptruser/.cache/puppeteer \
  -e SITE_BASE_PATH=/bitcoin-gui-evidence/ \
  -v "$PWD:/site:ro" -v "$PWD/.validation/browser:/qa:rw" \
  -w /home/pptruser ghcr.io/puppeteer/puppeteer:24.16.0 \
  node /site/scripts/browser-test.cjs
```

Recorded validation results are in `validation/`. Each Actions run also retains browser screenshots and results as the `browser-validation` artifact for 14 days.

This is a standalone HTML/JavaScript site; it has no Bitcoin Core lint, clang-tidy, or sanitizer CI scripts. No Bitcoin Core application code changed. The October 10 functional rerun uses the original binary with a two-line test input correction; its [validation record](data/reruns/20261010-send-create/validation.json) records the missing historical CI scripts and remaining limits. The original application-test results and their limits are preserved separately in the evidence snapshot. The new acceptance scripts run against the unchanged pinned binary; their validation record explicitly retains the cache regression, missing native CI entry scripts, IPC limitation, and reset-fixture SIGTERM.
